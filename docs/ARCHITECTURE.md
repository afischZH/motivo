## 1. Leitprinzipien

1. **Ein Render-Pfad**: Vorschau und Export nutzen exakt denselben Code. (MagicPattern hatte laut Changelog Bugs, weil Vorschau und Export auseinanderliefen.)
2. **Deterministisch**: Jedes Ergebnis ist vollständig beschrieben durch `{ toolId, version, params, seed }`. Gleiche Eingabe ergibt immer dasselbe Bild. Das ermöglicht Speichern als kleines JSON, Share-Links, API und Undo.
3. **Client-first Rendering**: Rechenarbeit läuft im Browser (SVG, Canvas 2D, WebGL2, Web Worker). Server nur für statische Seiten und Share-Links; keine Konten, keine Nutzerdaten auf dem Server (seit 2026-10-28).
4. **Schema-getriebene Tools**: Ein Tool ist eine Datei mit Parameter-Schema und Render-Funktion. Die UI baut sich daraus automatisch. Nur so skaliert eine kleine Crew auf 30+ Tools.
5. **Isomorphe Engine**: Die Generatoren sind reines TypeScript ohne DOM-Abhängigkeit (wo möglich), damit sie im Browser, im Worker, auf dem Server (API) und in Plugins laufen.

## 4. Das Herzstück: Tool-Definition

Jedes Tool implementiert ein gemeinsames Interface. Damit sind Editor, Speicherung, API, KI und SEO-Seite automatisch vorhanden.

```ts
// packages/tool-registry/src/types.ts
import { z } from "zod";

export type RenderKind = "svg" | "canvas2d" | "webgl" | "image-effect" | "css" | "text";
export type ExportFormat = "svg" | "css" | "png" | "jpg" | "webp" | "gif" | "mp4" | "webm" | "react" | "json" | "tailwind";

export interface ToolDefinition<S extends z.ZodTypeAny> {
  id: string;                 // "geometric-patterns"
  version: number;            // Erhöhen bei Breaking Changes am Algorithmus
  category: ToolCategory[];   // ["patterns", "backgrounds"]
  renderKind: RenderKind;
  schema: S;                  // Zod-Schema aller Parameter
  defaults: z.infer<S>;
  presets: Preset<z.infer<S>>[];
  controls?: ControlHints<z.infer<S>>; // Gruppierung, Slider-Steps, Labels-Keys, Sichtbarkeitsregeln
  randomize: (rng: Rng, current: z.infer<S>, locks: Set<keyof z.infer<S>>) => z.infer<S>;
  render: Renderer<z.infer<S>>;       // siehe unten
  exports: ExportFormat[];
  needsImageInput?: boolean;           // Halftone, Dither ...
  animation?: AnimationSupport<z.infer<S>>; // GIF (seit M4-AP04): { sources: ["seeds", "colors", "time", "custom"], frame? }
  bundles?: BundleExport<z.infer<S>>[];      // Mehrere Dateien als ZIP (seit M4c-AP02, Abschnitt 5)
}

// Renderer je nach Art:
//  svg:      (params, seed, size) => string            // reiner SVG-String, serverfähig
//  css:      (params) => { css: string; previewSvg?: string }
//  canvas2d: (ctx: OffscreenCanvasRenderingContext2D, params, seed, size, t?) => void
//  webgl:    { fragment; uniforms(params, ctx); palette?; loopSeconds?; reference? } // im Worker, siehe 4.15
//  image-effect: (input: PixelBuffer, params, ctx) => PixelBuffer   // im Worker, siehe 4.14
//                optional grid(params, design) und vector { render, shapes, maxShapes }, siehe 4.16
```

**Konsequenzen**
- Die Editor-UI liest `schema` + `controls` und erzeugt Slider, Color-Picker, Selects, Toggles, Palette-Editor, Upload-Felder.
- `randomize` respektiert **Locks** (Schloss-Icon pro Parameter), wie beim Palette-Generator des Vorbilds.
- `version` sorgt dafür, dass gespeicherte Designs auch nach Algorithmus-Änderungen identisch aussehen (alte Versionen bleiben im Code, oder Migration der Params).

### 4.1 Zufall
- Seeded PRNG (`mulberry32` oder `sfc32`), Seed als 32-bit Integer im Design gespeichert.
- **Nie** `Math.random()` in Engine-Code (Lint-Regel).
- Leertaste = neuer Seed (und optional neue Params via `randomize`).

### 4.2 Bildeingabe (`imageInput`, ab M2-AP06)
Tools, die Parameter aus einem Nutzerbild ableiten (z. B. Palette aus Bild), deklarieren `imageInput` in ihrer `ToolDefinition`: `derivedKeys` (abgeleitete Params), `deriveOn` (Params, die eine Neuberechnung auslösen), `maxEdge`, `sample()` (eingebautes Beispielbild als Startzustand) und `derive(pixels, params, rng)` (rein, deterministisch). Die Editor-Shell (`packages/editor-ui/src/image-input/`) zeigt dafür generisch Ablage, Dateiwahl, Einfügen aus der Zwischenablage, Vorschaubild und Fehler (aria-live), ohne Tool-spezifischen Code.
- Ablauf: Grösse (max. 5 MB), Typ per Magic Bytes und Pixelzahl aus dem Header (max. 64 MP, gegen Dekompressionsbomben) prüfen, dann im Worker dekodieren (`createImageBitmap` + `OffscreenCanvas`) und auf `maxEdge` verkleinern. SVG wird nur über `<img>` mit Object-URL gerastert (keine Scripts, keine externen Ressourcen, nie als Markup), asynchron dekodiert (`img.decode()`) und direkt in Zielgrösse (höchstens `maxEdge`) gezeichnet. Das bleibt im Hauptthread, in allen Browsern: Kein Browser rendert SVG ausserhalb eines Dokuments (`createImageBitmap(blob)` lehnt SVG im Worker ab, `OffscreenCanvas` im Worker kennt kein `<img>`). Geprüft in M2-AP12 (Chromium, SVG mit 20 000 Kreisen, 1,2 MB): Parsen rund 220 ms und Rastern rund 330 ms sind je ein Task im Hauptthread; eine Variante, die die Pixel im Worker ausliest (Bitmap per Transfer), brachte keinen messbaren Gewinn und wurde verworfen. Übliche SVG-Dateien (Logos, Icons) bleiben weit unter 50 ms. Ohne Worker/OffscreenCanvas Fallback über `<img>` im Hauptthread auch für Rasterbilder.
- `derive` läuft im selben Worker (Timeout 10 s, Dekodieren 20 s; ein hängender Worker wird beendet und beim nächsten Aufruf neu gestartet) und erneut bei neuem Bild, neuem Seed (Leertaste) oder Änderung an `deriveOn`. Das Ergebnis landet per `applyDerived` im Store (ohne eigenen Undo-Schritt, da es aus Bild und Seed folgt), `render` bleibt eine reine Funktion der Params: Vorschau == Export.
- Datenschutz: Pixel liegen nur im Speicher des Tabs. Teilen-Links setzen `derivedKeys` beim Kodieren und Dekodieren auf die Standardwerte zurück, ein geöffneter Link zeigt also das Beispielbild. Nichts wird an Server gesendet oder gespeichert.
- Abgrenzung: `needsImageInput` bleibt für Bildeffekte reserviert, deren Renderer das Bild selbst als Eingabe braucht (M4/M5). Seit M4c-AP04 kann ein Tool mit `photoSource` (4.14) sein Bild für `derive` aus dem Foto-Param beziehen; der Bildwähler entfällt dann.

### 4.3 Listen-Params und Thumbnail-Picker (ab M2-AP04)
Zwei generische Erweiterungen der Auto-Controls, zuerst genutzt von den Ebenen des CSS-Muster-Tools (`docs/TOOLS.md` B1). Die Shell enthält dafür keinen Tool-Code.
- **Listen-Control** (`kind: "list"`): Ein Param, der ein Zod-Array von Objekten ist (`z.array(z.object(...)).min(m).max(n)`), wird automatisch als Liste plus Unterformular gezeigt. Länge kommt aus dem Schema (ohne `.max()` gilt die Obergrenze 20, damit UI und Links begrenzt bleiben). Das Unterformular für den gewählten Eintrag baut dieselbe Panel-Logik aus dem Item-Schema (`ControlSource`), die Hinweise dazu stehen in `ControlHint.list` (`ListHint`): `item` (Control-Hinweise der Felder, `visibleWhen` erhält den Eintrag), `visibilityField` (Boolean-Feld hinter dem Augen-Button), `titleField` (Auswahlfeld, das einen Eintrag benennt und als Mini-Vorschau zeigt), `newItem` (rein, Standard: erster Eintrag der Defaults) und `itemLabelKey` (i18n mit `{index}`).
- **Store**: `listOp(key, op)` mit `add`, `remove`, `duplicate`, `move` und `set` (ein Feld eines Eintrags). Das Schema entscheidet (Länge, Werte); was nicht passt, ändert nichts. Jede Strukturänderung ist ein Undo-Schritt, aufeinanderfolgende `set` desselben Felds werden wie bei `setParam` zusammengefasst. Welcher Eintrag gewählt ist, ist UI-Zustand der Komponente und gehört nicht zum Design.
- **Locks**: Felder einzelner Einträge haben Lock-Keys `<liste>.<index>.<feld>` (`ItemLockKey`, z. B. `layers.1.color`); der Lock auf der Liste selbst behält alle Einträge. Beim Verschieben, Einfügen, Duplizieren und Entfernen wandern die Locks mit ihrem Eintrag (`remapLocks`), Locks auf nicht mehr vorhandene Einträge (nach Undo, Variante, Vorlage) fallen weg (`pruneItemLocks`). `keepLocked` versteht beide Arten, `randomize` erhält sie als `ReadonlySet<LockKey>`.
- **Bedienung und Barrierefreiheit**: Liste als `<ol>` mit Zeilen-Buttons (ein Tab-Stopp, Pfeil hoch/runter, Pos1/Ende wählen, Alt + Pfeil verschiebt, Entf/Rücktaste entfernt), darunter Buttons für Hinzufügen, Duplizieren, Hoch, Runter, Entfernen (deaktiviert an den Grenzen) und Augen-Buttons mit `aria-pressed`. Jede Strukturänderung wird einmal in einer `aria-live="polite"`-Region angesagt (nicht bei Feldänderungen), der Fokus landet danach auf der neuen, verschobenen oder benachbarten Zeile bzw. bleibt auf dem Hoch/Runter-Button.
- **Sofort wirkende Steuer-Params** (`regenerateOn`, seit M2-AP12): Params, die nur steuern, wie `randomize` würfelt (z. B. die Harmonie des Palette Generators), stehen in `ToolDefinition.regenerateOn`. Ändert die Shell einen davon (`setParam`, `resetParam`), ruft der Store `randomize` mit dem aktuellen Seed und demselben gesalzenen RNG wie bei der Leertaste auf; gesperrte Keys und der geänderte Param bleiben. Das Ergebnis ist deterministisch und ein Undo-Schritt.
- **Alte Param-Formen**: `ToolDefinition.migrateParams(raw)` hebt ältere Formen (Teilen-Links, gespeicherte Designs) vor der Schema-Prüfung an; rein, darf nicht werfen, das Schema prüft das Ergebnis trotzdem. `parseToolParams(tool, raw)` fasst beides zusammen und wird vom Share-Codec und von `loadDesign` verwendet.
- **Thumbnail-Picker** (`kind: "thumbnails"` mit `ControlHint.optionPreview(value, params, root)`): Auswahl-Params (Enum) als Raster kleiner Vorschauen mit Radiogruppen-Semantik (ein Tab-Stopp, Pfeiltasten, Pos1/Ende, `aria-label` aus dem Optionsnamen). `optionPreview` liefert `{ css }` (Inline-Style, CSP-konform) oder `{ svg }` (nur über `<img>`, nie als Markup); es muss rein und billig sein (deutlich unter 1 ms). Kacheln berechnen ihre Vorschau erst, wenn sie sichtbar werden (IntersectionObserver). Ohne `optionPreview` fällt das Control auf ein Select zurück.

### 4.4 Brand-Palette in jedem Tool (ab M3-AP06)
Jedes Tool mit Farb-Params bietet "Brand-Palette anwenden", ohne eigenen Code (`packages/tool-registry/src/brand-palette.ts`).
- **Generische Zuordnung** (`colorTargets`, `mapBrandPalette`): Ziele werden aus Schema und Control-Hinweisen gefunden, sichtbare Params in Schema-Reihenfolge. Palette-Params (`kind: "palette"`) erhalten die ganze Palette (auf das Schema-Maximum gekürzt oder bis zum Minimum wiederholt), Farb-Params (`kind: "color"`) und Farbfelder von Listeneinträgen erhalten die Farben der Reihe nach, bei Bedarf von vorne. Der Hintergrund bleibt, er ist die Kontrastwahl des Nutzers. Abgeleitete Farben (`imageInput.derivedKeys`, z. B. Palette aus Bild) sind keine Ziele.
- **Hook** `ToolDefinition.brandPalette?(colors, current): Partial<P>` für Tools, die mehr brauchen; der Palette Generator setzt damit zusätzlich die Anzahl Farben. Danach gelten dieselben Regeln.
- `applyBrandPalette(tool, params, colors, locks)` ist rein: prüft 2 bis 10 HEX-Farben, wendet Hook oder Zuordnung an, behält gesperrte Params und Listenfelder (`keepLocked`) und prüft das Ergebnis mit `parseToolParams`. Ein Registry-Test wendet Paletten mit 2, 5 und 10 Farben auf Defaults und alle Presets jedes Tools an.
- **Store** (`applyBrandPalette` in `editor-store.ts`): ein Undo-Schritt; die geänderten Farb-Params werden gesperrt, damit die Leertaste (`randomize`) die Markenfarben behält (Locks sind nicht Teil der Undo-Historie).
- **Shell**: `BrandKitContext` (optional, ohne Brand Kit erscheint nichts) liefert Paletten an den Abschnitt "Brand-Palette" (Auswahl, Standard vorausgewählt) und an jeden Color-Picker (Brand-Swatches). Upload-Felder (`kind: "image"`) bieten Logos und Shapes aus dem Brand Kit an; sie laufen durch dieselbe Pipeline wie ein Datei-Upload (Sanitizer im Worker, Zuschnitt).

### 4.5 Code-first-Effekte: Element, Exporte je Params, Hinweise (ab M4-AP06)
Drei optionale, generische Erweiterungen, zuerst genutzt von Glas- und Rahmen-Effekten (`docs/TOOLS.md` J2). Die Shell enthält dafür keinen Tool-Code.
- **`CssOutput.element`** (`CssElement`): ein Element über der CSS-Fläche (Position und Grösse in px, eigene Deklarationen, `content` als Kästchen relativ dazu). Die Vorschau zeichnet es als echtes `div` auf der Bühne, damit `backdrop-filter` wirkt; die Kästchen liegen als Geschwister darüber (gleiche Versätze wie im SVG-Zwilling, unabhängig von der Rahmenbreite). `motionCss` (Animation) setzt die Vorschau nur, wenn `prefers-reduced-motion` nicht `reduce` ist (und erst nach der Hydration).
- **`CssOutput.rules`**: globale Regeln (`@property`, `@keyframes`) als `<style href precedence>` (React 19 hebt sie in den `<head>` und legt gleiche Regeln zusammen). Sie dürfen nur von Konstanten des Tools abhängen. CSP unverändert (`style-src 'unsafe-inline'` deckt Style-Elemente ab).
- **`ToolDefinition.exportsFor(params)`**: Teilmenge von `exports` für die aktuellen Params (Glas nur Code, Rahmen und Glow auch PNG/WebP). `supportsExport(tool, format, params?)` und `listExportChoices(tool, params?)` berücksichtigen sie; der Export-Dialog und das Kürzel „als PNG kopieren“ übergeben die Params.
- **`ToolDefinition.advisories(params, ctx)`**: Hinweise zu den aktuellen Params (`{ id, messageKey, values }`), rein und billig. Die Shell zeigt sie über den Einstellungen in einer `role="status"`-Region (aria-live polite), ohne Hinweise nichts.
- Neue Kategorie `css-effects` („CSS-Effekte und Layouts“, Slugs `css-effekte`/`css-effects`) für die Tools aus J.
- **`CssBox.motionCss`** (ab M4c-AP03, animierter Farbverlauf): Kästchen eines Elements dürfen eine eigene Animation tragen; die Vorschau setzt sie wie `CssElement.motionCss` nur, wenn der Betrachter Bewegung erlaubt (`MotifContentBox.motion`). Damit bewegen sich die Flecken als einzelne Kästchen per `transform`.
- **`CssBox.text`** (ab 2026-10-29, eigener Kartentext bei J2): ein Kästchen darf eine fertig umbrochene Textzeile tragen. Die Vorschau setzt sie als Textinhalt des `div` (nie als Markup, `MotifContentBox.text`); Schrift, Grösse und `white-space: pre` stehen in den Deklarationen, damit Vorschau und SVG-Zwilling dieselben Zeilen zeigen.
- **`ToolDefinition.contentParams`** (ab 2026-10-29): Params mit eigenem Inhalt des Nutzers (z. B. Kartentitel). Vorlagen lassen sie stehen wie `localParams` und die Vorlagen-Erkennung ignoriert sie; anders als `localParams` gehen sie in den Teilen-Link.
- **Werte über Variablen statt eigener Regeln**: Weil `rules` nur von Konstanten abhängen darf (mehrere Vorschauen teilen ein Stylesheet, gleiche Keyframe-Namen würden sich überschreiben), schreibt ein Tool mit params-abhängigen Keyframes feste Regeln mit Namensraum (`@keyframes musterli-ag-pan { from { background-position: var(--musterli-ag-from) } … }`) und setzt die Werte als Custom Properties auf Element oder Kästchen. Die Code-Exporte schreiben dieselben Werte direkt in lesbare Keyframes; ein Unit-Test löst die Variablen auf und vergleicht beide Fassungen (`TOOLS.md` L3).

### 4.6 Formenbibliothek (ab M4-AP01)
Eigene Formen für alle Tools mit Shapes (`packages/engine/src/shapes/`, Lizenz in `assets/LICENSES.md`). 170 Formen in 12 Packs: `basics`, `geometric`, `organic`, `blobs`, `stars`, `lines`, `retro`, `bauhaus`, `nature`, `symbols`, `tiles`, `decorative`.
- **Format**: absolute SVG-Pfaddaten (M, L, H, V, C, Q, A, Z) in einer 100er-Box, Nonzero-Füllung (Löcher laufen gegen ihre Kontur), keine Konturen, keine Glyphen. Zentriert gespeichert (x und y von -50 bis 50), damit ein Renderer mit einem Transform platziert, dreht und skaliert; `"box"` liefert dieselbe Form in 0 bis 100.
- **API** (rein, deterministisch, gecacht): `SHAPE_PACK_IDS`, `SHAPE_IDS` (als `z.enum` nutzbar, Typ `ShapeId`), `listShapePacks()` (Packs mit Shape-Ids in Anzeigereihenfolge), `getShape(id)` (`{ id, pack, primary, accent?, path, tile }` oder `undefined`), `isShapeId`, `shapePackOf`, `shapePath(id, origin?)` (beide Ebenen, unbekannte Ids fallen auf `circle` zurück), `shapeLayers(id, origin?)` (`{ primary, accent? }` für Duotone), `shapesInPacks(packs)`, `tileShapeIds()`. Dazu `parsePathData`, `pathBounds`, `flattenPath`, `translatePath`, `windingNumber` für Tests und Umrechnungen.
- **Ebenen**: 18 Formen haben eine zweite Ebene `accent`, die die erste nicht überdeckt (Würfel, Zielscheibe, Tulpe ...). Duotone zeichnet sie mit geringerer Deckkraft oder zweiter Farbe; einfarbige Tools nehmen `path` (beide Ebenen).
- **Kacheln**: Die Formen des Packs `tiles` (`tile: true`, 18 Stück) füllen die Box und treffen die Ränder an festen Punkten (Ecken, Kantenmitten), damit Vierteldrehungen benachbarter Zellen anschliessen (Truchet).
- **Stabilität**: Ids nie umbenennen oder entfernen (gespeicherte Designs, Teilen-Links); neue Formen hinten im Pack anfügen. Die 24 Formen von Seamless Patterns (M3-AP12) sind byte-gleich übernommen, ein Fixture-Test sichert das.
- **Controls** (`packages/tool-registry/src/shapes.ts`): `SHAPE_OPTION_LABEL_KEYS` (Namen unter `Shapes.names.<id>` in den Web-Messages), `shapePackGroups(only?)` für den Picker, `shapePreview(id, fill, background)` (kleines SVG, Accent mit 50 % Deckkraft). Der Namespace `Shapes` geht mit den Editor-Messages an den Client (ca. 4 KB).
- **Picker**: Der Thumbnail-Picker kennt generisch `ControlHint.optionGroups` (eine Gruppe sichtbar, Auswahlfeld darüber, die Gruppe folgt dem Wert bei Variante, Undo, Vorlage) und `ControlHint.brandShapesParam` (Name eines Bild-Params): Mit Brand Kit erscheint die Gruppe "Brand Kit" mit den eigenen Shapes; ein gewählter Shape läuft durch dieselbe Pipeline wie ein Upload (`useAssetLoader`: Prüfung, Sanitizer im Worker, Zuschnitt) in diesen Param, danach liegt der Fokus im Upload-Feld.
### 4.7 Vorschläge (ab M4-AP05)
- **`ToolDefinition.suggestions(params)`**: liefert Ein-Klick-Vorschläge `{ id, labelKey, values?, swatch?, patch }` (rein, billig, läuft bei jeder Änderung), zuerst genutzt vom Kontrast-Checker (F6) für die nächste Farbe, die AA oder AAA erreicht. Die Shell zeigt sie als Abschnitt "Vorschläge" über den Einstellungen (nach den Hinweisen und der Brand-Palette; Buttons mit Farbfeld, Hinweis per `aria-describedby`); ein Klick übernimmt `patch` per `setParams` als ein Undo-Schritt und meldet es über die Statuszeile (aria-live). Eine leere Liste zeigt nichts. Anders als `advisories` ändern Vorschläge die Params.
- CSS-Schatten (J1) nutzt `CssOutput.element` aus 4.5: `css` ist die Musterli-Bühne (nur Vorschau), das Element trägt `background-color`, `border-radius` und `box-shadow`; der Code kommt als Zusatzexport.

### 4.8 Bereiche in der Vorschau bearbeiten (ab M4-AP03)
- **`ToolDefinition.regionEditor`** (optional, `defineRegionEditor` in `registry.ts` löscht die Typen für die Registry): `{ titleKey, regions(params, ctx), schema, controls, values(params, id, ctx), set(params, id, patch, ctx), reset(params, id | null), editedCount(params), maxEdited }`. `regions` liefert `PreviewRegion[]` (`id`, Rechteck in Design-Pixeln, `labelKey` plus `labelValues`, `edited`); `schema` und `controls` beschreiben das Formular wie bei Listen-Params (4.3), die Shell baut es mit demselben `ControlForm`. Alles rein und billig (Geometric Patterns cacht das Raster pro Params-Objekt in einer `WeakMap`). Ein `set`, das nicht passt (unbekannte Zelle, ungültiger Patch, Grenze erreicht), gibt die Params unverändert zurück.
- **Shell** (`packages/editor-ui/src/shell/region-editor.tsx`): `RegionLayer` liegt über dem Vorschaubild (ausserhalb des `role="img"`), zeigt beim Zeigen den Umriss der Zelle und Markierungen bearbeiteter Zellen (nur bei Hover oder Fokus). Ein einziger Knopf `region-picker` ist im Tab-Ablauf; Pfeiltasten wählen die nächste Zelle in der Richtung (Mittelpunkt muss jenseits der Kante liegen, Wertung Abstand längs plus 2 × quer), Home/End die erste und letzte, Enter oder Leertaste öffnen. Klick öffnet die Zelle unter dem Zeiger. Das Popover (Radix, modal, unten, Breite höchstens 20rem bzw. Bildschirm minus 24 px) fängt den Fokus, schliesst mit Escape und gibt den Fokus an den Wähler zurück; Ansagen über eine aria-live-Zeile. Texte unter `Editor.regions`.
- **Undo**: Jede Änderung geht per `setParams(patch, { coalesceKey: "region:<id>:<feld>" })` in den Verlauf; aufeinanderfolgende Änderungen mit gleichem Schlüssel (Ziehen am Farbregler) werden zu einem Schritt zusammengefasst. Zurücksetzen (eine Zelle oder alle) ist ein eigener Schritt.
- **Speicherung**: Die Bearbeitungen sind gewöhnliche Params (Geometric Patterns: `tileOverrides`), also im Teilen-Link, im gespeicherten Design und im Entwurf, und werden beim Import mit dem Tool-Schema geprüft. Das Schema begrenzt Anzahl, Schlüsselmuster und Felder (strikte Objekte); verbotene Schlüssel wie `__proto__` lässt Zod fallen. Der Control-Hinweis `kind: "hidden"` hält den Param aus dem Panel und den Locks.
- **Escape im Popover**: Liegt der Fokus in einem verschachtelten nativen `<dialog open>` (Zuschnitt-Dialog eines Upload-Felds), schliesst Escape nur diesen: `onEscapeKeyDown` verhindert das Schliessen des Popovers und schickt dem Dialog ein `cancel`-Ereignis (Radix' `preventDefault` würde sonst auch das native Escape des Dialogs unterdrücken).
- **Kachel-Keys im Bento-Grid** (M4-AP06b): `t<n>` nach Lesereihenfolge der Kacheln, Inhalt bleibt beim Neu-Würfeln bei der Nummer (Details `TOOLS.md` J3). Das Formular verbindet zwei Params: Text und Symbol in `tileContent` (Teilen-Link), Bilder in `tileImages` (lokal).
- **Zellen-Ids in Geometric Patterns**: `<Zeile>-<Spalte>` der Grundzelle plus `.<Viertel 0-3>` pro Teilung (0 oben links, 1 oben rechts, 2 unten links, 3 unten rechts), Muster `^\d{1,3}-\d{1,3}(\.[0-3]){0,4}$`. Die Id hängt nur von der Position im Raster ab: stabil bei Farbe, Form, Pack, Drehung, Abständen, Kontur und Bildgrösse (solange `columns` und das Seitenverhältnis gleich bleiben), im Uniform-Modus auch bei neuem Seed. Ändert sich das Raster, bleiben fremde Ids gespeichert und zählen zur Grenze (128), wirken aber nicht.
- **Mehrfachauswahl im Thumbnail-Picker**: Ein Array-Param aus Enum-Werten mit Vorschau wird zum Thumbnail-Raster mit Kontrollkästchen (`ThumbnailControl.multiple = { min, max }` aus dem Schema, `toggleChoice` hält die Grenzen ein); `optionGroups` gelten wie beim Einzelwert.

### 4.9 Generative Bausteine (ab M4b-AP01)
Gemeinsame, reine Helfer in `packages/engine` für die Tools der generativen Welle (`docs/TOOLS.md` K), je mit Unit-Tests:
- **`noise2d.ts`**: `createNoise2D(rng)` (2D-Gradientenrauschen nach Perlin, acht Gradienten, Permutation per Fisher-Yates aus dem Seed, Periode 256, Wertebereich [-1, 1]) und `fbm2D(noise, x, y, { octaves, gain, lacunarity })` (normiert).
- **`contours.ts`**: `marchingSquares(values, cols, rows, level)` liefert Konturen als flache Punktlisten in Rasterkoordinaten, offen oder geschlossen; Sattel über den Zellmittelwert. Ein Rand mit sehr tiefen Werten schliesst alle Konturen. Interne Puffer werden zwischen Aufrufen wiederverwendet (nur berührte Einträge werden zurückgesetzt).
- **`polyline.ts`**: Polylinien als flache Arrays `[x0, y0, x1, y1, ...]`; `simplifyPolyline` (Ramer-Douglas-Peucker, offen und geschlossen), `subdividePolyline`, `slicePolyline` (Teilstück nach Bogenlänge), `polylineLength`, `polylinePathData` (implizites Lineto), `smoothPathData` (quadratischer B-Spline über `Q`), `numberFormatter` (schnelles Runden ohne `toFixed`). In heissen Schleifen `Math.sqrt` statt `Math.hypot` (in V8 mehrfach langsamer).

Seit M4b-AP05 so bemessen, dass der schlimmste Fall jedes Tools in Node unter rund 45 ms bleibt; `tool-registry/src/tools/main-thread-budget.test.ts` rendert die gefundenen schlimmsten Fälle (Zufallssuche über Schema-Grenzen und Grössen). `numberFormatter(1)` und `formatCoord` schreiben Zehntel über zwischengespeicherte Ganzzahl-Texte (gleicher Text wie `String`, rund doppelt so schnell).

### 4.11 Tool-Grössen und grosse Bilder in der Vorschau (ab M4b-AP04)
- **`ToolDefinition.sizePresets`** (optional, `ToolSizePreset` = `CanvasSize` plus `id` und `nameKey`): eigene Ausgabegrössen eines Tools (Screenshot-Verschönerer: Product Hunt 1270 × 760, LinkedIn 1200 × 627, 16:10 1920 × 1200). Der Grössen-Wähler der Shell zeigt sie als erste Gruppe "Für dieses Tool" (`Editor.size.groups.tool`), Options-Werte `tool:<id>`; eine Grösse, die zu einer Tool-Grösse passt, wird als diese erkannt (vor den allgemeinen). Die Grösse bleibt ein gewöhnlicher Teil des Designs (Teilen-Link, Designs), kein Param.
- **Allgemeine Grössen** (seit M4b-AP06): `SIZE_PRESETS` (`SizePreset` = `CanvasSize` plus `id`, `group`, `nameKey` = `sizes.<id>`) mit Gruppen aus `SIZE_PRESET_GROUPS` (`social`, `desktop`, `mobile`, `tablet`, `print`, `ratio`; Reihenfolge = Anzeige). Gruppen sind reine Anzeige, Ids stabil. Eine Grösse darf in zwei Gruppen vorkommen, in einer Gruppe nur einmal (Test). `SizePresetOptions` (editor-ui) rendert die `<optgroup>`s mit "Name (B × H, Ausrichtung)" für den Grössen-Wähler und den Export-Dialog; `matchSizePreset(size, toolPresets, preferred)` behält die zuletzt gewählte Option, solange ihre Grösse passt. Im Export-Dialog setzt eine Vorlage `ExportSizeMode` `{ kind: "custom", width, height, preset }`; `planRasterSize` entscheidet wie bisher zwischen Skalieren (gleiches Seitenverhältnis) und Neuberechnen in dieser Grösse (ein Render-Pfad). Katalog und Quellen: `docs/TOOLS.md` (Grössen-Katalog).
- **Ebenen-Vorschau für grosse Uploads**: Ein Tool mit grossem Bild (Screenshot bis 3840 px) rendert als `kind: "css"` mit `previewSvg`. Das SVG ist das fertige Bild für alle Exporte; die Vorschau zeigt dieselbe Szene als Bühne (CSS-Hintergrund ohne das Bild) und das Bild als `element`. Grund: Chromium lädt ein `<img>`-SVG mit eingebettetem 4K-PNG bei jeder Änderung neu (150 bis 360 ms im Hauptthread).
- **Grosse data-URIs in CSS-Vorschauen** (`packages/editor-ui/src/shell/large-data-urls.ts`, generisch): Base64-data-URIs ab 256 KB in `url("…")` einer CSS-Ausgabe ersetzt `Motif` durch `blob:`-URLs (nur PNG, JPEG, WebP, GIF und AVIF: eine `blob:`-URL gehört zum App-Origin, andere Typen bleiben data-URIs) (Dekodieren in Schritten von 64 KB zwischen Tasks, Blob und Render danach in eigenen Tasks; jede Vorschau und jedes Upload-Feld hält seine URL mit `retainObjectUrl`, nach der letzten Freigabe wird sie am Ende der Task widerrufen, seit M5b-AP01 statt erst ab 24 URLs); bis die URL bereit ist, fehlt der Wert kurz statt den Hauptthread zu blockieren (ein Style-Wert mit 4 MB kostet ca. 100 ms pro Element). PNG und JPEG über 1600 px Kante (`PREVIEW_MAX_EDGE`) zeigt die Vorschau als verkleinerte Kopie aus dem Bild-Worker (sonst wartet der Hauptthread beim Software-Raster auf das Skalieren); `useDisplayUrl` macht dasselbe für Vorschaubilder im Upload-Feld. Die Tool-Ausgabe und alle Exporte behalten die data-URI in voller Grösse. `parseCssDeclarations` überspringt lange Werte in Anführungszeichen per `indexOf`.
- **Mehrere Bilder in der Ebenen-Vorschau** (M4b-AP07, Website-Mockups): Das `element` liegt transparent über der ganzen Fläche, seine `content`-Kästchen tragen die Szene in Malreihenfolge: jedes Bild als eigenes Kästchen, die Vektorteile dazwischen (Geräte davor) als SVG-Kästchen in voller Grösse. So verdecken vordere Geräte die Bilder dahinter wie im SVG; keine Änderung an der Shell.
- **Upload-Pipeline**: `finishAsset` prüft das Ergebnis per Schema in einer eigenen Task (Regex über eine data-URI mit mehreren MB, ca. 20 ms). Neue Grenze `screenshotAssetSchema` (Raster bis 3840 px, data-URI bis 24 Mio. Zeichen); `UPLOAD_RASTER_MAX_EDGE` ist das Maximum aller Upload-Schemas; beim Designs-Import gilt seit M5b-AP01 die Grenze jedes Bild-Params aus seinem Schema (`rasterEdgeLimits`, Abschnitt 6).

### 4.14 Foto-Effekte: Fotoquelle und Raster-Stufe (ab M4c-AP04)
Grundlage für Duotone (L4) und ASCII-Art (L5), wiederverwendbar für Halftone, CMYK-Halftone und Dither (M5). Keine neue Dependency, nichts verlässt das Gerät.
- **Pixel-Helfer** (`packages/effects`, rein und deterministisch, ohne DOM, je mit Unit-Tests): `PixelBuffer` (RGBA, wie `ImageData`), `coverRect`/`resizeCover` (Zuschnitt wie `object-fit: cover`, Box-Filter, nur für Node), `luma` mit Gewichten (`LUMA_WEIGHTS`: Rec. 709, Rec. 601, Mittelwert), Tonkurve (`toneCurve`: Helligkeit, Kontrast, Gamma als LUT mit 256 Werten), Korn (`grainAt`: Wert-Rauschen aus Hash und Seed, Zellen in Design-Pixeln, also gleich bei jeder Auflösung), Verlaufs-LUT in OKLab (`gradientLut`), `applyGradientMap` (Duotone, Tritone, Verlauf), Bayer-Matrizen, ASCII-Raster und -Ausgaben, `demoPhoto(w, h)`.
- **Beispielbild**: `demoPhoto` zeichnet prozedural einen Bergsee im Abendlicht (Himmel, Sonne mit Schein, Wolken, drei Bergketten, Spiegelung mit Wellen, Glitzern). Kein Stockfoto, keine Asset-Lizenz. Die Szene wird höchstens mit 720 px Kante berechnet und bilinear vergrössert, Feintextur pro Pixel aus dem Hash (ca. 290 ms bei 1500 × 1000 in Node, einmal pro Grösse gecacht).
- **`ToolDefinition.photoSource`** (generischer Hook): `{ param, sample(width, height) }`. `param` ist ein Upload-Param (`kind: "image"`, in `localParams`), dessen Standard `null` das Beispielbild bedeutet; `sample` liefert das Beispielbild in genau dieser Grösse (aufgerufen mit der Designgrösse, eingepasst in `PHOTO_SAMPLE_MAX_EDGE` = 2048). Wirkung: (1) bei `render.kind === "image-effect"` ist das Bild die Render-Eingabe; (2) bei Tools mit `imageInput` speist das Foto `derive` anstelle des separaten Bildwählers (der Controller dekodiert das Foto wie eine Datei; ohne Foto setzt er die `derivedKeys` auf die Standardwerte, das Tool rendert dann sein Beispielbild selbst); (3) ein neues Foto setzt die Designgrösse auf seine Pixelgrösse (gleicher Undo-Schritt, `photoDesignSize`, Kanten unter 16 px werden vergrössert). Helfer in `tool-registry/src/photo-source.ts`: `photoAssetOf`, `isImageEffectTool`, `renderImageEffect`, `fitSize`.
- **Foto-Uploads**: `effectPhotoAssetSchema` (nur Raster, bis 4096 px Kante, data-URI bis 24 Mio. Zeichen; ein 12-MP-Foto behält fast die volle Auflösung). `ImageHint.rasterOnly` lehnt SVG schon beim Lesen ab (Fehler `raster-only`, nach Magic Bytes, nicht nach Endung), `accept` ohne SVG, eigener Hinweistext. Mit `photo: true` wird als JPEG neu kodiert. Grenzen und Prüfungen der Upload-Pipeline (5 MB, Magic Bytes, 64 MP) gelten unverändert. Beim Designs-Import darf ein Rasterbild laut Kopfdaten nicht grösser sein als deklariert (vorher genügte `UPLOAD_RASTER_MAX_EDGE`, das mit 4096 px nun über der Screenshot-Grenze liegt).
- **Render-Art `image-effect`**: `render(input, params, ctx) => PixelBuffer`. `input` ist das Bild, schon auf die Ausgabegrösse zugeschnitten; `ctx` trägt die Designgrösse, so ist `input.width / ctx.width` der Massstab der Vorschau. Rein und deterministisch (Zufall nur aus `ctx.seed`, unabhängig von der Auflösung).
- **Raster-Stufe der Editor-Shell** (`packages/editor-ui/src/raster-effect/`): `renderMotif` liefert für Bildeffekte `MotifOutput` `kind: "raster"` (nur die Design-Beschreibung). `RasterMotif` zeichnet in ein `<canvas>` in der angezeigten Auflösung (Skalierung mal `devicePixelRatio`, höchstens Designgrösse); pro Motiv ist eine Anfrage unterwegs, Änderungen dazwischen fallen auf die neueste zusammen, das letzte Bild bleibt bis zum nächsten stehen. Der Worker (`raster-effect.worker.ts`) hält das dekodierte Foto (2 Fotos, LRU) und das Beispielbild als `ImageBitmap` (3 Grössen), schneidet per `drawImage` auf `OffscreenCanvas` zu (hohe Glättung), führt den Effekt aus und gibt eine `ImageBitmap` (Vorschau, per Transfer) oder eine kodierte Datei (`convertToBlob`) zurück. Das Foto (data-URI) geht pro Worker nur einmal über `postMessage`, danach per Schlüssel; der Worker meldet `missing-photo`, wenn er es nicht mehr hat. Zwei Worker, damit ein langer Export die Vorschau nicht aufhält; Timeouts 30 s und 120 s. Kein Hauptthread-Fallback: Ohne Worker oder `OffscreenCanvas` zeigt die Vorschau eine leere Fläche und der Export meldet `unavailable`.
- **Export**: `exportDesignRaster` ist der `exportRaster`-Dienst des Export-Dialogs: Bildeffekte rendern mit demselben Worker-Pfad in der Ausgabegrösse (Designgrösse als Kontext), alle anderen Tools wie bisher als SVG. So sind Vorschau und PNG-Export bei gleicher Grösse pixelgleich (E2E prüft Gleichheit, nicht nur Ähnlichkeit). Budget `IMAGE_EFFECT_MAX_PIXELS` = 50 MP (darüber `too-large`), JPG mit Hintergrund (Standard weiss), Qualität wie beim SVG-Export. `kindSupports` erlaubt für `image-effect` nur PNG, JPG und WebP.
- **Statische Motive** (Landing-Seiten, Katalog, OG-Bilder): `staticMotifSvg` rendert Bildeffekte in Node auf dem Beispielbild (Zuschnitt mit `resizeCover`, höchstens 480 px Kante, `EFFECT_MOTIF_EDGE`) und verpackt das Ergebnis als PNG (eigener Streaming-Encoder mit `CompressionStream`, `@musterli/exporters/png-stream`) in ein SVG; ca. 160 bis 340 KB pro Motiv. Die Pixel können leicht von der Editor-Vorschau abweichen (Box-Filter statt Canvas-Glättung).
- **Hauptthread**: Gemessen in Chromium (Produktions-Build) mit einem 12-MP-Foto: Hochladen, Zuschneiden, Effekt und Bearbeiten ohne Long Task über 50 ms (E2E). Im Entwicklungsmodus (`next dev`) kosten React-Renderings des Bedienfelds 60 bis 90 ms, das ist der Dev-Overhead von React.
- **Review M4c** (M4c-AP05): Die Vorschau hat zusätzlich ein Budget von 4096² Pixeln (`RASTER_PREVIEW_MAX_PIXELS`), ein vergrössertes 8192-px-Design rendert sonst 67 MP pro Änderung. Der Worker prüft jede Anfrage (Grössen 1 bis 8192 px, Ausgabe höchstens `IMAGE_EFFECT_MAX_PIXELS`, Params gegen das Tool-Schema) und antwortet sonst `invalid-request`, bevor er etwas dekodiert. Abbrechen eines Exports beendet den Export-Worker sofort. Raster-Motive und laufende Exporte halten den gemeinsamen Client (`retainRasterEffectClient`); 30 s nach der letzten Freigabe werden beide Worker samt dekodierten Fotos beendet. ASCII-Art nimmt Fotos nur bis 1024 px (`asciiPhotoAssetSchema`), wie in `docs/TOOLS.md` L5 festgelegt. In Node (statische Motive, Tests) teilt `renderImageEffect` das skalierte Beispielbild über einen kleinen Cache (4 Einträge).
- **Bewusst nicht gemacht**: SVG-Export für Duotone (ein SVG-Filter kann weder in OKLab mischen noch das deterministische Korn nachbilden, siehe `docs/TOOLS.md` L4), GIF für Bildeffekte (GIF braucht SVG-Ausgabe). Vorschaubilder in "Meine Designs" zeichnet seit M5b-AP01 der Raster-Effekt-Worker (Abschnitt 6).

### 4.15 WebGL2-Grundlage und Shader-Stufe (ab M5-AP01)
Grundlage für den Shader-Farbverlauf (C4) und weitere Shader-Tools. Keine neue Dependency, alles im Browser, keine Kosten pro Nutzer.
- **Paket `packages/shaders`**: Haupteinstieg rein und ohne Browser-APIs (Node-Tests), Laufzeit getrennt unter `@musterli/shaders/runtime`.
  - `uniforms.ts`: `packUniforms(values, infos, provided)` macht aus einem Objekt `{ name: Zahl | boolean | Zahlen[] }` typisierte Setter-Aufrufe für die aktiven Uniforms eines Programms (Typ und Arraylänge aus `getActiveUniform`). Fehlender Wert, falsche Länge, nicht endliche Zahl oder Bruch für int/uint werfen `UniformError`; Sampler und die Laufzeit-Uniforms überspringt es.
  - `palette.ts`: Farbrampe als 1D-Textur (256 × 1 RGBA8, OKLab-Verlauf aus `gradientLut` von `@musterli/effects`) und `rampColor` als CPU-Gegenstück mit derselben linearen Interpolation.
  - `tiles.ts`: `planTiles` (Kacheln höchstens `SHADER_TILE_EDGE` = 1024 px), `renderInStrips` (eine Kachelreihe wird zu einem Streifen, oberste Zeile zuerst, `readPixels` liefert die unterste zuerst), `flipRows`.
  - `build-errors.ts`: `ShaderBuildError` mit Stufe (vertex, fragment, link) und lesbarem Log: die Zeile aus dem Compiler-Log wird mit Nachbarzeilen und Zeilennummern markiert.
  - `noise.ts` und `glsl/common.ts`: dieselben Bausteine in TS und GLSL. Ganzzahl-Hash (lowbias32, in GLSL `uint`, in TS `Math.imul`), Simplex-Rauschen 2D mit Seed (8 Gradienten, Gitter verschoben um 32768), fbm mit fester Drehung. `GLSL_PRELUDE` deklariert die Laufzeit-Uniforms und `musterliPixel()` (Pixelposition in der ganzen Ausgabe, auch in einer Kachel) und `musterliRamp(v)`.
  - `runtime.ts`: `createShaderRuntime(canvas)` (`null` ohne WebGL2) mit Vollbild-Dreieck aus `gl_VertexID` (kein Vertex-Buffer), Programm-Cache (4, Schlüssel ist der Fragment-Text), Palette nur bei Änderung neu hochgeladen, `draw(frame)` mit optionaler Kachel, `readPixels`, Kontextverlust (`webglcontextlost` mit `preventDefault`, nach `restored` werden die Caches verworfen, `draw` wirft `ShaderContextLostError`).
  - **GLSL als TS-Strings**, kein Hot Reload: der Shader-Worker wird beim Bearbeiten nicht ausgetauscht, ein eigener Loader für `.glsl` wäre Aufwand ohne Nutzen. Eine Shader-Änderung braucht ein Neuladen der Seite.
- **Render-Art `webgl`** (`WebglRenderer` in `tool-registry/src/types.ts`): `{ fragment, uniforms(params, ctx), palette?(params), loopSeconds?(params), reference?(input) }`. `uniforms` ist rein und deterministisch: Zufall nur aus `ctx.seed` (als Salze an den Shader), Zeit nur aus `ctx.t`, im Shader gibt es weder Uhr noch Zufall. Die Laufzeit setzt selbst `u_resolution`, `u_tileOrigin`, `u_tileSize`, `u_design` und `u_palette` (`RUNTIME_UNIFORMS`). Neue optionale Felder (generische Hooks):
  - `palette`: Farben der Rampe, daraus die Palettentextur (Cache mit 16 Einträgen).
  - `loopSeconds`: Länge der Vorschau-Schleife in Sekunden, 0 heisst still. Nur die Live-Vorschau bewegt sich; jeder Export zeigt `t = 0`.
  - `reference`: CPU-Zwilling desselben Algorithmus (gleiche Konstanten, gleiche Rundung) für Node: statische Motive, OG-Bilder und Snapshot-Tests. Ohne ihn hat das Tool keine statischen Motive.
  - Helfer in `tool-registry/src/webgl.ts`: `isWebglTool`, `webglFrame` (Shader, Uniforms und Palette eines Designs), `hasWebglReference`, `renderWebglReference`, `webglLoopSeconds`.
- **Vorschau gleich Export**: Grain- und Dither-Zellen liegen in Design-Pixeln (`floor(d + 0.001)`, der Zuschlag verhindert Kippen an exakt ganzzahligen Grenzen bei verkleinerter Ausgabe), alles andere in Design-Koordinaten. Kacheln bekommen ihren Ursprung als Uniform, das Bild ist darum mit und ohne Kacheln gleich (Unit-Test mit dem CPU-Zwilling, E2E mit der GPU). Gemessen mit SwiftShader in Chromium: GPU und CPU-Zwilling weichen im Mittel um 0.005 Stufen ab, höchstens um 1.
- **Shader-Stufe der Editor-Shell** (`packages/editor-ui/src/shader/`, aufgebaut wie die Raster-Stufe aus 4.14): `renderMotif` liefert `MotifOutput` `kind: "shader"`. `ShaderMotif` zeichnet in ein `<canvas>` in der angezeigten Auflösung (wie `rasterPreviewSize`, Kante höchstens `SHADER_FRAME_MAX_EDGE` = 2048, damit jede GPU es in einem Durchgang schafft). Mit dem neuen Prop `animate` (nur die Hauptvorschau), einer Schleife und erlaubter Bewegung laufen Bilder nach der Uhr: höchstens 30 pro Sekunde, eines unterwegs, höchstens 1 MP (`SHADER_ANIMATION_MAX_PIXELS`); die Uhr läuft bei Param-Änderungen weiter. Mit `prefers-reduced-motion` steht die Vorschau auf `t = 0`. Der Worker (`shader.worker.ts`) hat eine WebGL2-Laufzeit auf einem `OffscreenCanvas`; die Vorschau kommt per `transferToImageBitmap`, Exporte entstehen in Kacheln: PNG über den Streaming-Encoder (`@musterli/exporters/png-stream`, kein grosses Canvas, 8192² möglich), JPG und WebP auf einem 2D-`OffscreenCanvas` mit `convertToBlob` (Budget `SHADER_COMPOSED_MAX_PIXELS` = 50 MP, darüber `too-large`). Nach jeder Kachelreihe meldet der Worker Fortschritt; der Export-Timeout gilt pro Pause ohne Fortschritt (60 s), die Vorschau hat 30 s. Bei Kontextverlust versucht der Worker es einmal mit einer neuen Laufzeit, danach `context-lost`. Der Worker prüft jede Anfrage (WebGL-Tool, Grössen, `t` in 0 bis 1, Params gegen das Schema). Zwei Worker (Vorschau, Export), gemeinsamer Client mit `retainShaderClient`, 30 s nach der letzten Freigabe beendet (Browser erlauben nur wenige GPU-Kontexte). Stürzt ein Worker ab (Fehler, unlesbare Nachricht), startet die nächste Anfrage einen neuen; erst nach 3 Abstürzen in Folge ohne gute Antwort (`SHADER_MAX_CRASHES`) bleibt der Kanal bis zur Freigabe aus. Meldet der Worker `context-lost`, wird er ersetzt, sobald er frei ist (seit M5b-AP01).
- **Ohne WebGL2**: Kein Hauptthread-Fallback. Alle Browser, die Musterli unterstützt, haben WebGL2 in Workern; ein 8K-Export im Hauptthread würde die Seite blockieren. Fehlt WebGL2, `OffscreenCanvas` oder der Worker, zeigt die Vorschau statt einer leeren Fläche den Hinweis `Editor.shader.unavailable` (DE/EN), und der Export meldet `unavailable`.
- **Export**: `exportDesignRaster` leitet WebGL-Tools an `exportShader` (gleiche Uniforms, Designgrösse als Kontext, Ausgabegrösse als `u_resolution`). `kindSupports` erlaubt für `webgl` PNG, JPG und WebP. GIF: `exportGif` nimmt neu die Option `renderFrame` (generisch, `GifFrameRenderer`), die ein Bild in GIF-Grösse als Bitmap liefert; `exportDesignGif` (Dienst `exportGif` des Export-Dialogs) setzt sie für WebGL-Tools auf den Shader-Worker. Die Quelle `time` ergibt nahtlose Schleifen, weil die Zeit nur über Kreisbahnen mit ganzen Umläufen in die Uniforms geht.
- **Statische Motive und OG-Bilder**: in Node über den CPU-Zwilling (`webglMotifSvg`, höchstens 480 px Kante, als PNG in einem SVG wie bei den Bildeffekten). Bewusst kein Headless-Browser im Build: langsam, braucht einen Browser in CI und auf Cloudflare nicht verfügbar. Ein Motiv kostet ca. 0.3 bis 1 s, nur beim Build.
- **Bewusst nicht gemacht**: Video (von Andreas verschoben), Code-Export des Shaders. Vorschaubilder in "Meine Designs" zeichnet seit M5b-AP01 der Shader-Worker (Abschnitt 6).

### 4.16 Effektraster und Vektorausgabe für Bildeffekte (ab M5-AP02)
Erweiterungen der Raster-Stufe (4.14) für Halftone, CMYK-Halftone und Dither (`docs/TOOLS.md` E2 bis E4). Keine neue Dependency, die Pipeline bleibt eine: gleicher Worker, gleicher Fotocache, gleiche Prüfung und gleiches Abbrechen.
- **`ImageEffectRenderer.grid(params, design)`** (generischer Hook, optional): feste Effektgrösse unabhängig von der Ausgabe. Für Effekte, deren Ergebnis von der Auflösung abhängt (Fehlerdiffusion): Ein Dither in Vorschaugrösse hätte ein anderes Muster als der Export. Mit `grid` zeichnet der Worker das Foto direkt in Rastergrösse (`effectInputSize` in `tool-registry/src/photo-source.ts`, gleiche Zuschnitt-Funktion), `render` arbeitet und antwortet in dieser Grösse, `renderImageEffect` skaliert auf die Ausgabe (`scaleGrid` in `packages/effects`: Nächster Nachbar beim Vergrössern, Box-Filter beim Verkleinern, rein in JS, also gleich in Worker und Node). Ergebnis: Vorschau und Export teilen dasselbe Raster; in gleicher Grösse pixelgleich, in 2× jeder Punkt verdoppelt (E2E). Grenze `IMAGE_EFFECT_GRID_MAX_PIXELS` = 4096², das Tool verkleinert sein Raster selbst (Dither: Designgrösse / Pixelgrösse, gleichmässig gekappt), der Worker lehnt grössere Raster als `IMAGE_EFFECT_MAX_PIXELS` ab (`invalid-request`).
- **`ImageEffectRenderer.vector`** (generischer Hook, optional): `{ render(input, params, ctx) => string, shapes(params, design) => number, maxShapes }`. SVG-Ausgabe eines Bildeffekts aus denselben Analysedaten wie das Raster (Halftone: dieselben Zellmittelwerte, dieselbe Formgrösse). `exporters/kindSupports` erlaubt SVG für `image-effect` nur mit `vector`. Das SVG entsteht im Export-Worker: Anfrage mit `encode.mime = "image/svg+xml"` und `out = effectVectorInputSize(design)` (Designgrösse, höchstens `IMAGE_EFFECT_VECTOR_MAX_EDGE` = 4096 px Analyse), Antwort als `Blob`. Der Worker prüft zusätzlich: Tool hat `vector`, `out` ist die Analysegrösse, `shapes ≤ maxShapes`; sonst `invalid-request`. Node-Helfer für Tests: `renderImageEffectSvg`, `effectVectorBudget`.
- **Export-Dialog**: Für Bildeffekte mit `vector` heisst die SVG-Karte intern `effect-svg` (Kategorie Vektor, gleiche Id `svg`, also gleich gemerkt). Kein Code-Feld (der Text entsteht asynchron im Worker); "Herunterladen" und "Kopieren" holen das SVG über den Dienst `exportEffectSvg` (`raster-effect/export.ts`, Fortschritt und Abbrechen wie beim Raster-Export, Dateiname `musterli-<tool>-<seed>.svg`). Unter den Karten steht die geschätzte Formzahl (`Editor.export.vectorShapes`); über dem Budget eine Warnung mit `role="alert"` (`vectorTooMany`) und gesperrte Knöpfe. So wird nie eine Datei mit Millionen Formen gebaut; PNG, JPG und WebP haben kein Formbudget.
- **Ein Render-Pfad**: Raster und SVG teilen Analyse und Geometrie (`packages/effects/src/halftone.ts`), aber das SVG wird vom Programm des Nutzers gerastert. Es ist eine eigene Ausgabe, kein Bild der Vorschau; die E2E-Gleichheit gilt für PNG.
- **Bewusst nicht gemacht**: SVG für Dither (jedes Pixel ein Rechteck), Hauptthread-Fallback (wie 4.14), ein Formbudget in `exportsFor` (hängt von der Designgrösse ab, `exportsFor` kennt nur die Params; darum zeigt der Dialog die Karte und erklärt das Budget).

### 4.17 Perspektive ohne 3D-Library (ab M5-AP03)
Reine Helfer in `packages/engine/src/tools/perspective-grid/` (`docs/TOOLS.md` D4), je mit Unit-Tests, keine neuen Hooks:
- **Projektion** (`perspectiveCamera`): Lochkamera über einer Ebene, Tiefe in Zellen; Bildzeile `Horizont ± f·h/d`, Spalte `cx + f·X/d`. Rollen der Kamera = ganze Szene im umschliessenden Rechteck der gedrehten Fläche berechnen und per `transform` drehen (Verläufe in `userSpaceOnUse` drehen mit).
- **Clipping**: Linien zwischen Nahebene (Tiefe des Bildrands) und fernem Ende, nie bis zum Horizont; Spalten ab der Tiefe, in der sie seitlich ins Bild treten (keine riesigen Koordinaten, keine NaN). Das ferne Ende rückt nach vorne, wo Zeilen dichter als ein Mindestabstand würden.
- **Ausblenden nach Tiefe mit einem Verlauf**: Auf einer Ebene hängt die Tiefe nur von der Bildzeile ab, also blendet ein einziger senkrechter Verlauf (Linienfarbe mit `stop-opacity`) alle Linien aus, statt Deckkraft pro Linie.
- **Begrenzter Blur für dünne Linien** (`perspectiveGlowSigma`): σ höchstens `MESH_FILTER_SIGMA_MAX` Ausgabepixel beim grösstmöglichen Export (`MESH_OUTPUT_EDGE_MAX`), wie `meshBlurPlan`; dünne Linien brauchen keinen Raster-Ersatz, der Glow wird nur schmaler. Der Blur-Filter nutzt per `<use>` dieselben Pfaddaten (SVG bleibt halb so gross).
- **Nahtlose Bewegung**: Zeilen bei `(j − t) · Abstand`; `t = 1` ist dasselbe SVG wie `t = 0`, das ferne Ende ist voll ausgeblendet, darum kein Springen.

### 4.18 Weiterverwenden und Ins Brand Kit (ab M5b-AP04)
Menü "Weiterverwenden" neben Export (`packages/editor-ui/src/handoff/`). Die Shell kennt kein Tool; alles folgt aus der Registry.
- **Ziele ableiten** (`packages/tool-registry/src/handoff.ts`, `imageTargetsOf`/`listImageTargets`): ein Tool nimmt ein Bild über (1) `ToolDefinition.imageTargets` (Param-Keys, z. B. `backgroundImage`, `screenshot`), (2) den Param von `photoSource` oder (3) den Bildwähler von `imageInput`. Ein Ziel-Param muss im Schema stehen, den Hint `image` haben **und in `localParams` stehen**; so landet ein übergebenes Bild nie im Teilen-Link. Das Quell-Tool selbst ist kein Ziel; jedes Tool mit PNG-Export kann Quelle sein (auch Bildeffekte, z. B. Halftone ► Duotone).
- **Rendern**: über `ExportServices.exportRaster`, also derselbe Pfad wie der Export-Dialog (SVG-Raster, Raster-Worker, Shader-Worker). Grösse = Design in die Kante des Ziel-Felds eingepasst (`resolveControl` bzw. `imageInput.maxEdge`), nie vergrössert. Über 5 MB: bei Foto-Zielen JPG 0.92, dann kleinere Stufen (0.7, 0.5, 0.35), sonst Fehler `too-large`.
- **Übergabe im Speicher des Tabs** (`handoffStore`): ein Eintrag, Token aus 128 Bit `crypto.getRandomValues`, Navigation clientseitig zu `…/<tool>#handoff=<token>`. Kein IndexedDB, keine Version, nichts auf der Festplatte: Neuladen oder Schliessen des Tabs vergisst das Bild, ein neuer Eintrag ersetzt den alten, nach 60 s (`HANDOFF_TTL_MS`) wird er verworfen. `take` gibt ihn genau einmal heraus, auch an ein falsches Tool nicht (dann ist er weg). Bewusst nicht `sessionStorage` (Base64, 5 MB Limit, überlebt Neuladen) und nicht IndexedDB (Waisen auf der Platte, Version-Bump).
- **Prüfen wie ein Upload**: `put` prüft Grösse und Magic Bytes (PNG, JPG, WebP; kein SVG, kein GIF). Das Ziel (`useHandoffReceiver`) nimmt das Bild durch `readAsset` (5 MB, Magic Bytes, 64 MP) und `finishAsset` (Decodieren und neu Codieren im Bild-Worker, Kante, Param-Schema), ohne Zuschnitt-Dialog. `imageInput`-Ziele erhalten eine `File` für den normalen Bildwähler.
- **Empfang**: Token beim Mounten lesen und sofort aus der Adresse entfernen (StrictMode-sicher), anwenden erst, wenn Entwurf oder gespeichertes Design geladen sind (`view.ready`), damit nichts das Bild überschreibt. `setParam` plus `commit` ist ein Undo-Schritt; ein Foto setzt wie beim Upload die Designgrösse. Abgelaufen, abgelehnt oder fehlerhaft: Hinweis, Design bleibt unverändert.
- **Ins Brand Kit**: optionaler Hook `ToolDefinition.paletteOutput(params)` bei den Farb-Tools (Paletten-Generator, Abstufungen, Tailwind-Palette, Palette aus Bild, Kontrast-Checker). `brandPaletteOutput` normalisiert auf `#rrggbb`, entfernt Doppelte, mindestens 2, höchstens 10 Farben (gleichmässig gewählt). Der Dialog speichert über `BrandKitStore.createPalette` (bestehende Limits, `StorageError` mit Meldung), bestätigt und verlinkt das Brand Kit; die Brand-Palette der offenen Seite lädt neu.
- **Offen**: Der Screenshot-Verschönerer hat kein Hintergrundbild; Ziel ist das Feld `screenshot`. Ein Hintergrundbild wäre ein eigener Param mit eigener Vorschau-Ebene.

### 4.19 Weitere Bildeffekte ohne neue Hooks (ab M6-AP01)
God Rays, Fractal Glass und Verpixeln (`docs/TOOLS.md` E5 bis E7) nutzen nur die bestehende Raster-Stufe (4.14) und die Hooks aus 4.16; die Shell bleibt unverändert, keine neue Dependency.
- **Neue reine Helfer** in `packages/effects` (je mit Unit-Tests): `filters.ts` (bilineares Abtasten mit geklemmten Rändern für ein Graustufenraster und RGBA, `boxBlur` als zwei Box-Durchgänge pro Richtung mit laufender Summe, Aufwand unabhängig vom Radius), `god-rays.ts`, `fractal-glass.ts`, `pixelate.ts` (Quantisierung, nächste Palettenfarbe, `pixelateSvg`).
- **Aufwand begrenzen statt `grid`**: God Rays rechnen das Strahlenfeld intern auf höchstens 640 px Kante und vergrössern bilinear; damit kostet ein 12-MP-Export kaum mehr als die Vorschau, und gleiche Ausgabegrösse ergibt dieselben Pixel. `samples` ist im Schema auf 128 gedeckelt.
- **Verpixeln mit `grid`** wie Dither: Der Blockmittelwert entsteht beim Zeichnen des Fotos in Rastergrösse im Worker, das Ergebnis wird mit `scaleGrid` vergrössert. Das SVG (`vector`) mittelt die Analysegrösse selbst per Box-Filter aufs Raster.
- **Zufall**: Fractal Glass verschiebt Streifen mit `hashSigned(k, 0, ctx.seed)`; God Rays nutzt einen festen Hash pro Rasterzelle (kein Seed), damit die Leertaste nur die Params ändert.

## 5. Render- und Export-Pipeline

```
Params + Seed ──► Renderer ──► Vorschau (DOM-SVG / Canvas / WebGL im Viewport)
                      │
                      └──► Exporter(format, size, options)
                              ├─ SVG: String (bereits kompakt) ► Datei
                              ├─ CSS: data-URI (url-encoded SVG) oder native CSS-Gradients
                              ├─ PNG/JPG/WebP: SVG ► Image ► Canvas ► Blob  |  Canvas/WebGL direkt
                              │                 Bildeffekt: Foto ► Worker (Effekt) ► Blob (4.14)
                              │                 WebGL: Shader-Worker in Kacheln ► PNG-Streifen / Blob (4.15)
                              ├─ GIF: N Frames (Seed-Varianten oder Zeit t) ► gifenc (Worker)
                              ├─ MP4/WebM: Frames ► VideoEncoder (WebCodecs) ► Muxer
                              └─ React/Web-Component: Template mit eingebettetem SVG/Shader
```

Wichtige Regeln:
- **Grosse Exporte** (4K/8K) in OffscreenCanvas im Worker, mit Fortschrittsanzeige und Abbruch.
- **Max. Canvasgrösse** (seit M3, `packages/exporters/src/raster.ts`): Grenze ist `SAFE_CANVAS_AREA` = 4096 × 4096 px (WebKit zeichnet auf grössere Canvas und Bitmaps nichts, 8K-Exporte waren in Safari leer). Darüber gilt:
  - **PNG in Streifen**: Das SVG-Bild wird streifenweise (höchstens die Grenzfläche, mit Worker höchstens 4 MP, ohne Worker 0.5 MP pro Streifen) mit Versatz auf ein kleines Canvas gezeichnet, per `getImageData` gelesen und an den Raster-Worker übertragen. Dort filtert ein eigener Streaming-Encoder (`png-stream.ts`, adaptive PNG-Filter wie libpng) die Zeilen und komprimiert sie mit `CompressionStream("deflate")` (zlib-Format). Höchstens ein Streifen ist unterwegs, kein Canvas und keine Bitmap hat die volle Grösse. Gemessen in Node: 8K in ca. 2 s im Worker. Ohne `CompressionStream` nimmt PNG den Weg von JPG/WebP.
  - **JPG und WebP**: kein eigener Encoder (Aufwand, WebP praktisch nicht machbar). Sie behalten das volle Canvas, aber 9 Prüfpixel des Ergebnisses werden mit denselben Pixeln verglichen, einzeln auf ein 1 × 1 Canvas gezeichnet. Weicht ein Drittel oder mehr ab (leeres Canvas), folgt ein zweiter Versuch im Hauptthread, danach der Fehler `too-large` mit lokalisierter Meldung („PNG oder kleinere Grösse wählen“) statt einer kaputten Datei.
  - Testhaken: `window.__musterliMaxCanvasArea` senkt die Grenze (nie höher), damit E2E-Tests den Streifenweg in Chromium bei 480 × 320 prüfen.
- **GIF-Export** (seit M4-AP04, `packages/exporters/src/gif*.ts`):
  - **Opt-in pro Tool**: `ToolDefinition.animation = { sources, frame?, customLabelKey? }` (ersetzt das frühere, ungenutzte `supportsAnimation`). Eine Zeile reicht: `animation: SEED_AND_COLOR_ANIMATION` (Seeds und Farbwechsel) oder `COLOR_ANIMATION` (nur Farbwechsel, für Tools ohne Zufall im Renderer). GIF steht nicht in `exports`, `supportsExport(tool, "gif")` folgt aus `animation` und braucht SVG-Ausgabe (svg oder css mit `previewSvg`) oder, bei WebGL-Tools, einen Bild-Renderer des Aufrufers (`renderFrame`, seit M5-AP01, 4.15). Aktiv in Blob, Blob-Komposition, SVG-Wellen, Polka Dots, Doodles, Konfetti, Sternenhimmel, Seamless Patterns, Mesh, Blurry und Streifen-Verlauf, CSS-Verlauf, CSS-Muster, Bento-Grid und Geometric Patterns (Seeds und Farben) und CSS-Schatten (Farben), animierter Farbverlauf (Zeit über den SVG-Zwilling, Farben), Shader-Farbverlauf (Zeit im Shader-Worker, Farben); nicht in Glas-Effekte und Kontrast-Checker. Mit `exportsFor` gilt: bieten die Params keine Rasterausgabe (kein PNG), gibt es auch kein GIF (`supportsExport(tool, "gif", params)`).
  - **Frame-Quellen** (`planAnimationFrames` in `tool-registry/src/animation.ts`, rein und deterministisch): `seeds` (gleiche Params, Seed + i), `colors` (die Farb-Params, gefunden wie bei der Brand-Palette, rotieren über alle Bilder um eine Position je `count / k` Bilder, dazwischen in OKLab gemischt, Bild 0 ist das Design selbst, die Schleife ist nahtlos; bei weniger als zwei verschiedenen Farben dreht der Farbton einmal um den Kreis), `time` (`RenderContext.t = i / count` für Renderer, die `t` nutzen), `custom` (eigene Funktion `animation.frame`).
  - **Ein Render-Pfad**: jedes Bild ist `render(params, createRenderContext(seed, Designgrösse, t))`, als SVG auf die GIF-Grösse skaliert, im Hauptthread dekodiert (SVG geht nur dort) und per `createImageBitmap` ausserhalb des Hauptthreads gerastert; die Bitmap geht an den GIF-Worker, der sie auf ein `OffscreenCanvas` zeichnet und die Pixel dort liest. Gemessen in Chromium bei 20 Bildern Mesh und Blurry in 1024 px: keine Long Tasks (vorher mit Zeichnen und `getImageData` im Hauptthread 50 bis 130 ms pro Bild), E2E prüft das. Fallback ohne Bitmap aus SVG: Zeichnen in Bändern von höchstens 0.26 MP im Hauptthread (Yield dazwischen), dann RGBA an den Worker. Dort lädt `gif-start` gifenc per `import()`, jedes Bild wird mit eigener Palette (bis 256 Farben, `rgb565`; mit Transparenz `rgba4444` und 1-Bit-Alpha, Disposal 2) quantisiert und LZW-kodiert. Höchstens ein Bild ist unterwegs. Bewusst ohne Hauptthread-Fallback: gifenc ist nur vom Worker-Einstieg aus erreichbar und landet so weder im Seiten- noch im Server-Bundle (alle unterstützten Browser haben Module-Worker); ohne Worker meldet der Export `unavailable`.
  - **Grenzen** (`gif-plan.ts`): 2 bis 60 Bilder, 20 bis 2000 ms pro Bild (Schritte von 10 ms, GIF speichert Hundertstel), Kante höchstens 1024 px (Auswahl 320, 480, 640, 800, 1024 px an der langen Seite), Budget `GIF_PIXEL_BUDGET` = 30 Mio. Pixel über alle Bilder; darüber sperrt der Dialog den Download mit Erklärung (DE/EN) und der Exporter wirft `budget-exceeded`.
  - **Dialog**: Kategorie "Animation" mit Karte GIF; Quelle (nur bei mehr als einer), Anzahl Bilder, Dauer pro Bild, Endlos wiederholen, Grösse, Zusammenfassung; Fortschritt und Abbrechen wie beim Raster-Export. Kopieren nur für PNG.
  - **Tests**: `readGifInfo` (`@musterli/exporters/gif-info`) liest Header, Grösse, Bildzahl, Verzögerungen und Loop ohne Pixel zu dekodieren, für Unit- und E2E-Tests.
- **Kein Wasserzeichen, keine Exportlimits** (seit 2026-10-28, `PRODUCT.md` 6): Grössengrenzen sind nur technisch (`CANVAS_EDGE_MAX` 8192 px). Exporte werden nicht protokolliert. Das frühere Feld `gating` der `ToolDefinition` ist seit M3-AP13 entfernt.
- Nach einem erfolgreichen Download oder Kopieren zeigt der Export-Dialog eine leise Zeile aus dem generischen Slot `afterExport` der Editor-Shell; die App füllt ihn mit dem Spendenhinweis (Link auf "Unterstützen", neuer Tab). Kein Popup, keine Sperre.
- **Clipboard**: `navigator.clipboard.write` mit PNG-Blob; Fallback Download.
- **Pakete (`bundles`, seit M4c-AP02)**: mehrere Dateien eines Designs als ein ZIP, zuerst das Icon-Paket des Favicon-Generators (`docs/TOOLS.md` L2).
  - **Opt-in pro Tool**: `ToolDefinition.bundles = [{ id, labelKey, descriptionKey?, files(params, ctx), snippet? }]` (`BundleExport`). `files` ist rein und billig und listet die Dateien in Archivreihenfolge (`BundleFile`): `text` (UTF-8, z. B. Manifest, HTML oder ein SVG, das das Tool mit seiner Engine-Funktion baut), `png` (`width`, `height`, optional eigene `params`) und `ico` (quadratische `sizes` bis 256 px, optional `params`). Bilddateien rendert der Exporter mit `render` des Tools in ihrer Grösse und mit dem Seed des Designs (ein Render-Pfad); Varianten wie Apple Touch oder Maskable sind gewöhnliche Params. Braucht SVG-Ausgabe (svg oder css mit `previewSvg`). Der Vertragstest prüft eindeutige Ids, sichere und eindeutige Pfade, gültige Params und wohlgeformtes SVG jeder Bilddatei für Defaults und alle Vorlagen.
  - **Export** (`exportBundle` in `@musterli/exporters`, `bundle.ts`): PNGs wie jeder PNG-Export (`rasterizeSvg`: SVG im Hauptthread dekodiert, im Raster-Worker kodiert), `.ico` aus diesen PNGs (`encodeIco`, eigener Encoder, PNG-Einträge, `ico.ts`), dann das ZIP im Raster-Worker (Nachricht `zip`, `handleZipMessage`); ohne Worker im Hauptthread (Deflate asynchron). Fortschritt pro Bild, Abbrechen wie beim Raster-Export. Dateiname `musterli-<tool>-<seed>-<bundle>.zip`.
  - **ZIP** (`zip.ts`, ohne Library): lokale Kopfzeilen, Daten, zentrales Verzeichnis, Endsatz; pro Datei STORE oder Deflate über `CompressionStream("deflate-raw")`, nur wenn kleiner (PNGs bleiben gespeichert); CRC-32 aus der Engine, UTF-8-Namen (Bit 11), Zeitstempel als DOS-Zeit (Standard 1980-01-01 für reproduzierbare Archive, der Export setzt die aktuelle Zeit). Kein ZIP64 (höchstens 65 535 Dateien und 4 GB); unsichere Pfade (absolut, `..`, Steuerzeichen, Backslash) und doppelte Pfade werfen `encode-failed`. `readZip` liest Archive für Tests zurück und vergleicht lokale und zentrale Kopfzeilen.
  - **Dialog**: neue Kategorie "Paket" (`Editor.export.categories.bundle`) mit einer Karte pro Bundle (`bundle:<id>`, wird wie jedes Format gemerkt). Zeigt Beschreibung und Dateiliste (`bundleFiles`) und das Snippet (`bundleSnippet`, z. B. die Head-Tags) als Code zum Kopieren; "Herunterladen" lädt das ZIP. Ohne Snippet ist Kopieren gesperrt (`copyBundleNone`).
  - **Nicht für andere Tools freigeschaltet** (Entscheid im AP): Ein automatisches Icon-Paket für alle quadratischen Tools wäre generisch machbar (die Dateiliste hängt nur von Grössen ab), aber Muster und Verläufe sind als 16-px-Favicon kaum lesbar, Manifest-Name und Farben fehlen dort als Params, und die Maskable-Sicherheitszone braucht Wissen über den Inhalt. Ein Tool kann das Paket später mit einem Eintrag in `bundles` anbieten.

**Sicherheit**
- **RLS auf allen Tabellen**: Besitzer liest/schreibt eigene Zeilen; `is_public = true` ist für alle lesbar.
- API-Keys nur gehasht speichern (SHA-256 + Pepper), Klartext nur einmal anzeigen.
- Uploads: SVG **immer sanitizen**, Bilder auf Grösse/Typ prüfen. Seit M3-AP12 gibt es dafür das Paket `@musterli/svg-sanitizer` (eigener Whitelist-Parser, keine Dependency, ohne DOM, also im Browser, im Worker und auf dem Server gleich; ESLint-Regeln wie die Engine). Wiederverwendbar für das Brand Kit (M3-AP05) und spätere serverseitige Uploads.
  - **Parser**: eigener strikter XML-Parser. Eine DOCTYPE mit interner Teilmenge (`[`) wird abgelehnt (XXE, Billion Laughs), eine einfache DOCTYPE (Illustrator-Export) übersprungen; nur die fünf XML-Entities und numerische Zeichenreferenzen, jede andere Entity lehnt ab. Grenzen: 1 MiB Eingabe, Tiefe 64, 20 000 Elemente, 2000 `<use>`. Kommentare und Processing Instructions fallen weg, CDATA wird Text.
  - **Whitelist-Neuaufbau**: Die Ausgabe wird aus dem Baum neu serialisiert (kanonisch, idempotent), nichts wird durchgereicht. Erlaubt sind nur Formelemente, Gruppen, `defs`, `symbol`, `use`, `text`/`tspan` (als Text, Schriften nur über `font-family`, im `<img>` ohne externe Schriftdateien), Verläufe, `pattern`, `clipPath`, `mask`, `marker`, `image` (siehe unten) und eine kleine Filtermenge; `a` und `switch` werden zu `g`. Verworfen werden u. a. `script`, `foreignObject`, `iframe`, `feImage`, Animationen (`animate`, `set`), `style` nach dem Auswerten und alle fremden Namensräume (inklusive Umschalten des Default-Namensraums). Attribute nur aus der Präsentations- und Geometrie-Liste, alle `on*` fallen weg.
  - **Werte**: `url()` nur als `#id` auf ein vorhandenes Element; keine Zeichen `<>{};\@` und Backticks, kein `javascript:`, `data:` oder `expression`, CSS-Funktionen nur aus einer Liste; `href`/`xlink:href` bei `use`, Verläufen und Mustern nur lokal (`#id`), `<use>` darf weder verschachtelt `use` noch einen Vorfahren referenzieren (Use-Bomben). `<image>` nur mit `data:image/(png|jpeg|gif|webp);base64` bis 1 MB, nie SVG oder HTML; die ersten Bytes müssen zur Signatur des angegebenen Typs passen (kein SVG oder HTML hinter `image/png`). Funktionsnamen werden linear geprüft (kein Regex-Backtracking).
  - **CSS**: Klassenregeln aus `<style>` (einfache Selektoren Tag, `.class`, `#id`; At-Regeln wie `@import` fallen weg) und `style`-Attribute werden als Präsentationsattribute übernommen, wenn der Wert die Prüfung besteht; die Ausgabe enthält kein CSS. Gegen DoS: höchstens 2000 Selektoren je Dokument (Duplikate zählen einmal), Regeln nach `#id`, `.class` oder Tag indexiert, höchstens 32 Klassen je Element und 1 Million Selektorvergleiche je Dokument (danach keine weiteren Klassenstile); ein offener CSS-Kommentar läuft bis zum Ende.
  - **Optionen**: `crop` (neue viewBox und Grösse für den Zuschnitt), `recolor` (setzt Füllung, Kontur, `stop-color`, `flood-color` und `color` auf eine Farbe; für einfarbige Motive). `sanitizeSvgCached` merkt sich die letzten Ergebnisse für Render-Pfade, die bei jedem Render erneut prüfen.
  - **Testkorpus** (`packages/svg-sanitizer/src/sanitize.test.ts`): Script als Element, in CDATA und mit `xlink`, `onload`, Gross-/Kleinschreibung bei Handlern, `foreignObject` mit HTML, `javascript:` direkt und per Entity kodiert, externe und data-URI-`use`, CSS-`url()` und `@import`, `style`-Attribut mit `url()`, `expression()`, externe `fill`/`filter`-Referenzen, `feImage`, `animate`/`set` auf `href`, SVG- und HTML-data-URIs in `<image>`, `iframe`, HTML-Namensraum, Umschalten des Default-Namensraums, XXE und Billion Laughs, verschachtelte und rekursive `use`, Grenzen, Idempotenz. Dazu `bypass.test.ts` aus dem Security-Review: kodierte `javascript:`-Varianten (Tab, Zeilenumbruch, `&#x6A;`), CDATA, Kommentare und PIs, Gross-/Kleinschreibung, Präfix- und Namensraum-Tricks, `xml:base`, `href` gegen `xlink:href`, `use` auf entfernte Inhalte, `set`/`animate` auf `xlink:href`, getarnte data-URIs, `url()` in `mask`/`clip-path`/`marker` in allen Schreibweisen, Anführungszeichen-Ausbrüche und DoS-Fälle mit Zeitgrenze.
  - **Im Editor** (Seamless Patterns): Datei per Magic Bytes und Grösse prüfen, SVG sofort sanitizen, Zuschnitt erneut über den Sanitizer, beim Rendern noch einmal (Verteidigung in der Tiefe). Sanitizen und Zuschneiden laufen in einem eigenen kleinen Worker (`asset-input/sanitize.worker.ts`, lazy beim ersten SVG geladen, Timeout 10 s, abbrechbar; bei Timeout oder Abbruch wird der Worker beendet und beim nächsten Aufruf neu gestartet). Nur wo es keine Worker gibt oder der Worker nicht startet, läuft derselbe reine Code im Haupt-Thread. Der Worker bereitet das zugeschnittene SVG auch fürs Rendern vor (`prepareSvgAsset` in `tool-registry/src/svg-asset.ts`: Sanitizer-Durchgang plus Umfärbe-Vorlage aus zwei Durchgängen mit #000000 und #ffffff); der Editor legt das Ergebnis im Cache nach Inhalt ab (`primeSvgAsset`). Rendern ist dann nur ein Cache-Treffer und ein String-Join pro Farbe, das Ergebnis ist zeichengleich mit `sanitizeSvg(svg, { recolor })` (Unit-Test). Fehlt der Eintrag (anderer Realm, verdrängt), bereitet `svgAssetFor` ihn neu vor: sicher, aber langsamer (Eingabe ist dann bereits Sanitizer-Ausgabe, die Kosten sind linear in der Grösse). Nutzer-SVG erscheint nur als `<image>`-data-URI in unserem SVG, das selbst per `<img>` angezeigt wird; nie als Markup, nie per `dangerouslySetInnerHTML`. Rasterbilder werden im Worker dekodiert, zugeschnitten und neu kodiert (höchstens 1024 px, nur PNG oder JPEG als data-URI, vom Schema geprüft).
  - **Lokale Params** (`ToolDefinition.localParams`): Params mit Nutzerdateien gehen nie in Teilen-Links (Share-Codec lässt sie seit M4-AP06b beim Kodieren ganz weg und setzt sie beim Dekodieren auf den Standard, auch wenn ein gebastelter Link sie enthält; die Shell zeigt beim Teilen einen Hinweis) und werden nie an einen Server geschickt. Im gespeicherten Design (IndexedDB) und im Datei-Export bleiben sie (Abschnitt 6). Vorlagen und die Leertaste lassen sie stehen.
  - **Bild-Felder** (`ControlHint.image: ImageHint`, M4-AP06b): `maxEdge` (Standard 1024), `photo` (Raster immer als JPEG neu kodieren, Transparenz auf Weiss; für Fotos als Hintergrund) und `paste` (Standard an). Schemas: `imageAssetSchema` (1024 px, 6 MB) und `photoAssetSchema` (2048 px, 9 MB data-URI), beide aus `imageAssetSchemaWith` und als Control-Art `image` registriert. Das Feld prüft das Ergebnis mit dem Schema des Params.
  - **Einfügen aus der Zwischenablage**: Ein Bild-Feld nimmt Einfügen nur an, wenn der Fokus nicht in einem Textfeld liegt und, solange ein modales Element offen ist (`[role="dialog"][data-state="open"]` oder `dialog[open]`), nur wenn das Feld darin liegt (`pasteBelongsTo`). Felder mit `paste: false` hören nicht zu (z. B. das zweite Bildfeld im Bento-Popover, damit ein Einfügen nicht zwei Felder füllt).
  - **Import geschachtelter Uploads**: `resanitizeUploads` prüft beim Datei-Import auch Bilder in Records und Objekten (Tiefe 3, z. B. `tileImages.t1.graphic`): SVG erneut durch den Sanitizer, Raster nur als PNG/JPEG-data-URI bis zur Grenze des Params aus dem Tool-Schema (`rasterEdgeLimits`, seit M5b-AP01; vorher pauschal `UPLOAD_RASTER_MAX_EDGE`); ein unsicheres Bild lehnt das ganze Design ab.
- **Security-Header** (M2-AP11) kommen aus einer Quelle, `apps/web/lib/security-headers.ts`, und werden an drei Stellen gesetzt: `next.config.ts` `headers()` (HTML, RSC), `proxy.ts` (Redirects, die OpenNext sonst ohne `headers()` ausliefert) und `public/_headers` (Dateien, die Cloudflare Workers Static Assets ohne Worker ausliefert). Seit M2-AP09 ist `public/_headers` nicht mehr eingecheckt: `scripts/headers.mjs` schreibt die Datei vor jedem `next build` und `next dev` aus demselben Modul und denselben Umgebungsvariablen wie `next.config.ts` (manuell: `pnpm --filter @musterli/web headers:write`). So stimmen Worker und Static Assets immer überein, auch wenn Analytics oder Sentry pro Build an- oder abgeschaltet sind.
  - CSP (Produktion): `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; worker-src 'self' blob:; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests`.
  - Weitere: `Strict-Transport-Security: max-age=63072000; includeSubDomains` (ohne `preload`, bis die Domain feststeht), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (Kamera, Mikrofon, Standort, Zahlung, USB, Sensoren, Topics gesperrt; Zwischenablage erlaubt), `Cross-Origin-Opener-Policy: same-origin`.
  - **Warum `'unsafe-inline'` bei Scripts**: Statisch vorgerenderte App-Router-Seiten enthalten neben dem Theme-Script seitenspezifische Inline-Scripts von Next (Turbopack-Bootstrap, React-Flight-Daten `self.__next_f.push`). Diese lassen sich nur mit Nonces erlauben, und Nonces erzwingen dynamisches Rendering (Next.js-Doku "Content Security Policy"). Ein Hash in der Policy würde `'unsafe-inline'` im Browser abschalten und die Hydration brechen. Der sha256-Hash des Theme-Scripts wird trotzdem in `lib/csp-hash.ts` aus demselben String berechnet und getestet, damit der Wechsel ein Einzeiler ist, sobald Next statische Inline-Scripts hashen kann. Schutz gegen XSS liefern weiterhin: kein Nutzer-HTML im DOM, Nutzer-SVG nur per `<img>`, kein `eval` (auch Zod läuft `jitless`), keine fremden Script-Quellen.
  - **Warum `'unsafe-inline'` bei Styles**: React rendert `style`-Attribute ins statische HTML (Vorschaugrössen, CSS-Tool-Vorschau, Farbfelder), Radix setzt `<style>` für die Scroll-Sperre. CSS führt keinen Code aus; Datenabfluss per CSS ist durch `img-src`, `font-src` und `connect-src` begrenzt.
  - Nur in `next dev`: `'unsafe-eval'` (React-Debugging) und `ws:` (HMR), ohne `upgrade-insecure-requests`. Ein Unit-Test stellt sicher, dass das nie in Produktion landet.
  - Lokale Variante für E2E mit `next start` auf `http://localhost` und `127.0.0.1`: ohne `upgrade-insecure-requests`, HSTS `max-age=0`, COOP `unsafe-none` (WebKit und Firefox). Sie gilt nur, wenn der Host lokal ist **und** der Header `CF-Connecting-IP` fehlt (`isLocalRequest`, `missing`-Bedingung in `localHostHeaderRule`). Grund (Security-Review M2-AP12): OpenNext übernimmt ein vom Client gesendetes `X-Forwarded-Host` als `Host`, bevor Next die `has`-Regeln prüft; mit `X-Forwarded-Host: localhost` hätte sonst jede Anfrage an die Produktion die gelockerte Variante erhalten. Cloudflare setzt `CF-Connecting-IP` bei jeder Anfrage aus dem Internet an den Worker selbst.

Cloudflare Turnstile (Warteliste) ist seit M3-AP13 entfernt. Ko-fi-Widget (seit 2026-10-28, nur wenn `NEXT_PUBLIC_DONATION_URL` eine Ko-fi-Seite ist, `kofiPageId`): `script-src`, `style-src` und `img-src https://storage.ko-fi.com`, `frame-src 'self' https://ko-fi.com` (`frame-src` erscheint nur mit einem Dienst, der ein Frame braucht). Google Fonts bleiben aus, das Widget wird mit leerer Stylesheet-Liste gezeichnet. In `next dev` nie. Unit-Tests prüfen beide Fälle, E2E prüft, dass ohne Variablen kein fremder Ursprung in der CSP steht.

Gesetzt über `liveViewHeaderRules` in `next.config.ts` (nach den allgemeinen und lokalen Regeln, je eine Regel für entfernte und lokale Hosts, nur die geänderten Header) und in `public/_headers` als eigene Regel pro Pfad, die CSP und Permissions-Policy zuerst mit `! Name` ablöst (Cloudflare verbindet doppelte Header sonst mit Komma). Das Ablösen und Neusetzen in einer Regel ist in der Cloudflare-Doku nicht beschrieben; da HTML-Seiten vom Worker kommen, betrifft es nur Static Assets unter diesen Pfaden (es gibt keine), offen ist die Prüfung im Preview. `proxy.ts` beantwortet nur Redirects und behält dort die allgemeinen Header. Neu darin: Exporte (nur Formate, die Render-Art und Export-Dialog bauen; immer PNG, JPG und WebP; SVG, wenn der Renderer Vektoren zeichnet; Ausnahmen mit Begründung in `NO_JPG`/`NO_SVG`), `exportsFor` innerhalb von `exports`, mindestens 3 verwandte Tools (`MIN_RELATED_TOOLS`), gleich viele FAQ in DE und EN, eindeutige Preset-Namen und keine Gedankenstriche (— überall, – ausser in Zahlenbereichen) in deutschen Tool-Texten. Verwandte Tools füllt `relatedTools` bei zu wenigen Tools mit gemeinsamer Kategorie über `NEARBY_CATEGORIES` (abwechselnd je nahe Kategorie) und zuletzt über die Registry-Reihenfolge auf, ohne Tool-spezifischen Code.
- **Barrierefreiheit**: axe-Checks in CI, alle Controls per Tastatur bedienbar.
- **Sicherheit**: SVG-Sanitizer mit bekannten XSS-Payloads testen; Importdateien (Designs, Brand Kit) mit manipulierten Fällen testen.
- **CI-Robustheit**: Unit-Tests müssen auch auf einem ausgelasteten CI-Runner sicher durchlaufen. Schwere Tests (Raster, Pixel, WebGL-Nachbildung über einen CPU-Zwilling) bleiben deutlich unter 5 s: kleine Ausgaben (Snapshot-Tests der Pixel-Tools bei 96 px Kante), deterministische Eingaben einmal berechnen und zwischenspeichern statt pro Vorlage neu, teure Wiederholungen (Determinismus) nur an einem Beispiel. Wo es nicht anders geht, eigener Timeout pro Test. Zeitmessungen nehmen den schnellsten von mehreren Läufen. Shader selbst (GLSL) werden in Chromium per E2E geprüft, nicht in Node. `renderImageEffect` teilt das skalierte Beispielbild (`IMAGE_EFFECT_TEST_EDGE` = 96 px); Halftone, CMYK und Dither brauchen zusammen unter 1 s (`halftone-dither.test.ts`). Grosse Pixelpuffer werden als Zeichenkette verglichen statt mit `toEqual` Element für Element.
- **Long Tasks in E2E**: Tests, die Long Tasks im Hauptthread messen (50-ms-Regel), tragen das Tag `@long-tasks` (`e2e/support/long-tasks.ts`). `pnpm test:e2e:chromium` führt zuerst alle anderen Tests parallel aus, danach die markierten allein mit einem Worker (`apps/web/scripts/e2e-chromium.mjs`), damit parallele Worker die Messung nicht verfälschen. CI läuft ohnehin mit einem Worker. Die Grenzen bleiben unverändert. Der 4K-Screenshot-Test misst Upload, Zuschnitt, zwei Änderungen und den Autosave-Entwurf in einem frischen Profil und zählt den besten von höchstens 3 Läufen (wie `main-thread-budget.test.ts`): Andere Prozesse auf der Maschine strecken Tasks von 25 bis 45 ms über 50 ms, ein echter Rückschritt fällt in allen Läufen durch (M5b-AP01).

## 13. Statistik und Fehler-Monitoring (seit M2-AP09)

Beide Dienste sind **aus**, solange ihre öffentliche Umgebungsvariable beim Build fehlt, und in `next dev` immer aus. Eine Quelle entscheidet über CSP, `public/_headers` und Laden im Browser: `apps/web/lib/telemetry/config.ts`. `next.config.ts` setzt beide Variablen per `env` immer (leer, wenn nicht gesetzt), damit Next sie inline einsetzt und Builds ohne Variable den Code gar nicht enthalten.

| Variable | Dienst | Format |
|---|---|---|
| `NEXT_PUBLIC_CF_ANALYTICS_TOKEN` | Cloudflare Web Analytics (Site-Token, manuelles JS-Snippet für nicht über Cloudflare geproxte Sites) | 32 Hex-Zeichen |
| `NEXT_PUBLIC_SENTRY_DSN` | Sentry, Datenregion EU | DSN mit Host `o<org>.ingest.de.sentry.io`; DSNs anderer Regionen werden verworfen |

**Cloudflare Web Analytics**: `components/telemetry/telemetry.tsx` fügt `https://static.cloudflareinsights.com/beacon.min.js` mit `data-cf-beacon='{"token":…,"spa":true}'` ein, sobald der Browser untätig ist, und nur auf dem Produktions-Host (gleiche Regel wie `X-Robots-Tag`, `lib/seo/indexing.ts`). Grund für die Host-Prüfung: Cloudflare prüft Hostnamen per Postfix-Match, ein Token für die workers.dev-Produktion würde auch Preview-Aliase (`<alias>-motivo-web…`) zählen. Der Beacon sendet an `https://cloudflareinsights.com/cdn-cgi/rum`. Keine Cookies, kein localStorage; Cloudflare speichert keine Query-Strings.

**Sentry**: nur clientseitige Fehler, kein Tracing, kein Session Replay, keine Breadcrumbs, keine Sessions. Seite und Bundle enthalten nur einen winzigen Reporter (`lib/telemetry/reporter.ts`: `ErrorReporter`-Interface, globale Handler für `error` und `unhandledrejection`, Warteschlange); `@sentry/browser` (11.9.0, MIT) wird erst beim ersten Fehler per `import()` geladen (`lib/telemetry/sentry.ts`). Gemessen: Sentry-Chunk 57,9 KB roh, **19,8 KB gzip**, nicht im initialen Laden. Konfiguration: manueller `BrowserClient` mit `linkedErrors` und `dedupe`; `dataCollection` schaltet Nutzerdaten (damit `infer_ip: "never"`, Sentry leitet keine IP ab), Cookies, Header, Query-Parameter, Bodies und Stack-Variablen ab (ersetzt `sendDefaultPii` ab SDK v11); `beforeSend` (`lib/telemetry/scrub.ts`) entfernt Query-Strings und Fragmente (`#d=`) aus allen URLs, Meldungen und Stack-Frames. Höchstens 25 Ereignisse pro Seitenaufruf (Gratis-Kontingent). Umgebung `production` auf dem Produktions-Host, sonst `preview`. Serverseitiges Sentry auf Workers ist nicht umgesetzt.

**Deploy**: Die Variablen nur für den Produktions-Build setzen (GitHub Actions, Schritt "Build for Cloudflare" bei `push` auf `main`), nicht für PR-Previews. Ohne Variable erzeugt `scripts/headers.mjs` die strikte CSP. Im Sentry-Projekt zusätzlich "Prevent Storing of IP Addresses" und Data Scrubbing aktivieren.

**Tests**: `lib/telemetry/telemetry.test.ts` (Konfiguration, Host-Regel, Lazy-Loading, Scrubbing), `lib/security-headers.test.ts` (CSP nur mit aktivierten Diensten), `e2e/home-legal.spec.ts` (ohne Variablen keine Anfragen an Cloudflare oder Sentry, kein Sentry-Chunk, keine Cookies, CSP ohne fremde Ursprünge).

**Cookies**: Das Sprach-Cookie von next-intl ist aus (`localeCookie: false`); `/` wählt die Sprache nur nach `Accept-Language`. Lokal gespeichert werden nur Design (Theme) und zuletzt genutztes Exportformat im localStorage.
